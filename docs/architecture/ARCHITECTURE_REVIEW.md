# Architecture Review — MASTER SPECIFICATION v2.0

**Status:** Phase 0 (Architecture Only) — no application code written.
**Scope:** Complete review of MASTER_SPECIFICATION v2.0 per review request. No production code, no prototype.
**Verdict format per finding:** Problem / Why it matters / Recommended solution / Architectural consequence / Spec change (Y/N).

This document is the single source of truth for Phase 0. It does not replace the Master Specification; it is the review gate the spec itself requires before code is written (§128, §159). Where this document recommends a change to the spec, that change must be ratified (i.e. the Master Specification edited) before the affected subsystem enters implementation.

## 1. Contradictions & Incompatible Requirements

| # | Problem | Why it matters | Recommended solution | Architectural consequence | Spec change |
|---|---|---|---|---|---|
| 1.1 | §7 says "Do not force the entire application's layer architecture into Media3's media-item model," but §92/§137 imply Media3 Transformer is also the export backbone, and §8 mandates *one* render graph feeding both preview and export. Media3 Transformer's composition model (Composition/EditedMediaItem) is fundamentally item/track based, not an arbitrary scene-graph compositor. You cannot simultaneously use Transformer's own compositing *and* have a fully custom RenderGraph be authoritative. | If both are "authoritative," implementers will diverge in practice: someone will render preview through the custom compositor and export through Transformer's shader effects, silently reintroducing the "looks different after export" bug §9 forbids. | Media3 is **encoder/muxer/container infrastructure only**. The custom RenderGraph renders every frame (preview and export) to an offscreen GPU surface; only the *already-composited* frame stream is handed to Media3 (via `Composition` with a single custom `GlEffect`/`VideoFrameProcessor` that is just "blit this externally-rendered texture," or via a raw `MediaCodec` surface input if Transformer's frame-processor extension point proves inadequate). Media3 never sees layers, effects, or reactive mappings. | RenderGraph owns 100% of visual composition; Export Engine owns only encode/mux/progress/cancel, consuming RenderGraph output frame-by-frame. | **Y** — §7 and §92 must be rewritten to state explicitly that Media3 is confined to decode/encode/mux, never compositing. |
| 1.2 | §60/§61 forbid arbitrary code execution and mandate "declarative manifest + shader code" as the *primary* mechanism, yet §55–§57 (Analyzer plugins, custom Layer plugins) require genuine *algorithmic* logic (a kick detector is a stateful DSP algorithm, not a shader) that cannot be expressed declaratively. | If Analyzer/Layer plugins can only ship declarative manifests + GLSL, they cannot actually implement novel audio analysis or novel CPU-side layer logic — this contradicts §55/§153/§156's explicit promise that plugins can add new analyzers and layer types. | Two plugin execution tiers: **Tier 1 (Declarative)** — Effect/Visualizer plugins expressed purely as parameter schema + shader (GLSL/uniform graph), no host-arbitrary logic, validated at install time, cannot escape the GPU sandbox. **Tier 2 (Sandboxed WASM)** — Analyzer, Generator-with-CPU-logic, and Layer plugins that need real algorithms run inside a WASM runtime (e.g. Wasmtime/Wasmer via JNI) with no filesystem/network/reflection capability, communicating with the host only through a fixed C-ABI (audio buffer in, float feature map out; or parameter buffer in, vertex/texture descriptor out). This matches §60's own fallback clause ("if arbitrary computational logic is eventually required, evaluate WASM") — the review concludes it is required *now*, not "eventually," because Analyzer/Layer plugins are unimplementable without it. | Plugin Runtime must ship a WASM sandbox from v1 of the Extension Platform, not as a deferred enhancement. Adds a real engineering cost (host↔WASM ABI, fuel/step-limiting for hang prevention, memory-limited linear memory) to Phase 7. | **Y** — §60/§74/§135 must state WASM is mandatory for Analyzer/Layer/Generator-with-logic plugins from v1, and define the ABI. |
| 1.3 | §9 (Frame Determinism: state at timestamp T must not depend on history) vs. §29 (Peak/Gravity model has explicit decay-over-time history) vs. §41 (temporal effects "must explicitly declare temporal state"). These are not contradictory once reconciled, but as written they read as a conflict: "no history" vs. "features with history are core requirements." | Left unreconciled, implementers will either (a) make everything historyless and lose peak/gravity/attack-release entirely, or (b) make everything stateful and lose determinism/seek-ability, breaking scrubbing, export-vs-preview parity, and undo/redo. | Determinism is defined precisely: **rendering a frame at time T is a pure function of (ProjectState, T, and the AudioAnalysisCache up to T)** — not of playback path. Stateful modulators (envelope followers, peak/gravity, smoothing) are re-derived from the *cached analysis timeline* by integrating from a fixed epoch (e.g. t=0 or last keyframe/reset boundary) each time a frame is requested, not by carrying live mutable state across UI events. In practice this means envelope/peak state is a deterministic function of the analysis samples in [0,T], computed via closed-form or fast-forward simulation, cached per-scrub-session for performance, but never treated as ambient mutable state that playback order can perturb. | Reactive Engine must implement "stateless-from-outside, state-derived-internally" modulators — i.e. every temporal modulator needs a documented deterministic integration rule, not an ad hoc `lastValue` field. This is a real DSP/architecture task, not a detail. | **Y** — §9 must add the precise definition above; §28/§29/§41 must cross-reference it. |
| 1.4 | §21 ("Beat detection is supplementary... must never replace raw spectral analysis") vs. §105/§107 (Beginner Mode UI exposes "Beat" as a first-class, equally-weighted reactive source next to Bass/Mid/Treble). | UI design and architectural intent disagree on beat's status, which will produce inconsistent guidance to feature implementers about how much engineering investment beat detection deserves and how failures should be surfaced (e.g., no-BPM music). | Beat/tempo/onset are a **derived, confidence-scored** feature family like any other (§17's "Musical" features), exposed identically to spectral bands in the Reactive Source list, but the UI must show `beatConfidence` and gray out or flag beat-driven mappings when confidence is persistently low, rather than silently producing jittery/wrong motion. | ReactiveSource metadata gains a `reliability`/`confidence` channel usable by any source (not just beat), and the UI's Reactive Mapping panel surfaces it. | N (clarify only) |
| 1.5 | §67 (auto-disable/quarantine a misbehaving plugin) vs. §71 (rollback on failed update) vs. §72 (removed-plugin placeholder) all assume plugins can be unloaded/replaced *at runtime without app restart*, but §60/§62's sandboxing model (favoring WASM or GLSL-only, not dynamically loaded native code) makes true hot-unload of a crashed GPU context nontrivial on Android (a GL context corrupted by a bad shader may require an EGL context recreation, not just "stop calling this plugin"). | If quarantine is specified as instantaneous and side-effect-free but the implementation actually requires tearing down and recreating the GL context (dropping all textures/FBOs for *every* layer, not just the offending plugin), "isolation" (§80) is violated in practice even though it's satisfied on paper. | Define quarantine as a **two-phase** operation: (1) immediate soft-disable — the plugin's render calls are skipped and its layer/effect renders as a "Missing/Disabled" placeholder for the *current* frame/session; (2) on next safe restart boundary (app relaunch or explicit user-triggered "reload renderer"), the GL context is recreated cleanly and the plugin is excluded from initialization. Never attempt to resurrect a GL context mid-frame. | Renderer must support a documented "degraded mode" render path (placeholder rectangles/labels) and a full teardown/rebuild path for GPU resources, both exercised by golden tests (§145). | **Y** — §67 should state quarantine has an immediate soft phase and a deferred hard phase. |

## 2. Missing Architectural Decisions

| # | Missing decision | Why it matters | Recommendation | Consequence | Spec change |
|---|---|---|---|---|---|
| 2.1 | No decision on **coordinate space / canvas model** (pixels? normalized 0–1? points independent of export resolution?) for layer transforms, masks, and reactive target ranges. | Every layer, effect, mask, and plugin parameter (§13, §39, §51) references position/size. Without a fixed space, preview-at-draft-resolution vs. export-at-4K will produce different visual results for anything expressed in pixels (e.g. blur radius, glow radius, particle size). | Canvas space is **resolution-independent, normalized to canvas height = 1.0** (or a fixed logical unit, e.g. "1080 logical units tall" regardless of actual export resolution), with an explicit, single `pixelsPerLogicalUnit = actualResolution/logicalResolution` scalar threaded through every shader that needs true pixel radii (blur, glow, pixelation, scanlines). | Every built-in effect and the Plugin Parameter API must declare whether a Float parameter is in logical units, normalized [0,1], or raw pixels — this becomes part of the Parameter type metadata (§49). | **Y** — add a explicit "Coordinate & Unit System" section. |
| 2.2 | No decision on **color space / working format** (linear vs. sRGB compositing, blend-mode math space) despite §90 requiring "consistent" preview/export color handling and §38 requiring 11 blend modes whose correctness depends entirely on which space they operate in. | Screen/Multiply/Overlay etc. produce visibly different (and "wrong" per industry convention) results if composited in sRGB gamma space vs. linear space. Getting this wrong is a top cause of "my export looks washed out / too dark" bug reports. | Composite in **linear light** internally (convert on texture sample, convert back on final output write), matching standard compositing practice (Porter-Duff over linear color), SDR passthrough now, explicit hook for HDR/wide-gamut later per §90. | FramebufferManager must support float or at-least-10-bit intermediate targets; ShaderManager must inject a standard sRGB↔linear conversion in every shader template. | **Y** |
| 2.3 | No decision on **audio/video sync model** for preview (audio plays on its own clock via AudioTrack/ExoPlayer while frames render on GPU vantage) — nothing specifies which clock is master. | Without a master clock decision, preview audio and visuals will drift, especially under GPU frame drops, which directly contradicts §9 determinism and §87 performance monitoring. | **Audio clock is master during interactive preview** (media playback position drives the requested render timestamp T; dropped video frames are fine, dropped/resampled audio is not). During **export**, there is no live audio clock — export is driven by a **virtual frame clock** (frame index / fps) and audio is rendered/mixed independently then muxed; this is intentionally a different sync source, which is safe specifically because export renders every frame (no drops) so virtual-clock-driven visuals and independently-mixed audio at the same nominal timestamps stay sample-accurate at mux time. | Playback controller must expose `currentPlaybackClock()` as the single source read by RenderGraph during preview; Export Engine must never share that clock, it computes T directly from frame index/fps. | **Y** — add explicit "Clock Authority" ADR. |
| 2.4 | No decision on what happens when **two ReactiveMappings target the same parameter with conflicting operators** (§26 shows addition — "Bass × 0.5 + Beat × 2.0" — but doesn't define multiply/max/min combination, ordering, or normalization of combined output before clamp). | Without a defined combine operator and evaluation order, the same project will render differently depending on plugin implementation order — this is exactly the kind of nondeterminism §9/§80 forbid. | Each ReactiveMapping declares a `combineOp` (Add, Multiply, Max, Min, Override) with an explicit **stack order** (list, top-to-bottom = evaluation order, like layer effects), default Add; the Modulation Pipeline (§27) formally is `foldl(combineOp, baseValue, mappings)` before Clamp. | ParameterBinding model needs an ordered list of mappings + per-mapping combineOp, and the UI (§105 "Advanced: multiple modulators") must expose reordering. | **Y** |
| 2.5 | No decision on the **plugin UI-schema→Compose rendering contract** version/extensibility boundary: §48 says host renders dynamically from declared schema, but nothing specifies what happens when a plugin declares a control type the current host version doesn't yet support (e.g. a future "Curve Editor" added in API 2.0 loaded by an API-1.0 host). | Silent failure to render a control means the user cannot access a parameter at all — this is a correctness and safety gap, not cosmetic. | UI schema controls must degrade gracefully: unknown control type → host renders a generic fallback (numeric input for scalar types, JSON textbox for opaque types) rather than omitting the control, and logs a diagnostic. This must be a **tested** path (§65/§76), not incidental behavior. | Plugin UI Generator needs an explicit "unknown control" fallback renderer as a first-class, tested component. | **Y** |
| 2.6 | No decision on the **units and evaluation timing of the AudioAnalysisCache** — is it a fixed-hop-size frame array (e.g. every 10ms) that reactive lookups interpolate, or per-sample? Nothing in §17/§18 specifies hop size, window size, or interpolation rule between cached samples. | Directly determines analysis storage size, latency characteristics of attack/release envelopes, and whether fast transients (e.g. hi-hats) are representable at all. Left unspecified, different subsystems (waveform trim UI vs. reactive engine vs. golden tests) will assume different hop sizes and disagree. | Fix **analysis hop = 10ms (100Hz feature rate)**, FFT window configurable per §106 ("FFT size") but default 2048 samples at 44.1/48kHz with 50% overlap, all derived per-band/onset/beat features resampled to the common 100Hz timeline for storage in AudioAnalysisCache; Reactive Engine linearly interpolates between adjacent 10ms cache samples for the requested render timestamp. | This single decision anchors cache file size estimates (§18), disk cache format, and reactive engine sample-and-hold vs interpolation behavior — must be pinned before any audio code is written. | **Y** |

## 3. Ambiguous Requirements

| # | Ambiguity | Why it matters | Recommendation | Consequence | Spec change |
|---|---|---|---|---|---|
| 3.1 | §26/§105 "Advanced: multiple modulators" — is a modulator graph limited to depth 1 (source → weight → sum) or can modulators themselves be modulated (e.g. "Bass modulates the *gain* of the Beat modulator")? | Determines whether Modulation is a flat list (simple, testable, bounded cost) or a recursive graph (powerful, but reintroduces the exact non-determinism/cycle risk the spec elsewhere avoids). | **v1: flat list only** (a fixed set of ModulationSource × weight/curve entries combined by `combineOp`, §2.4). Meta-modulation (modulating a modulator's own parameters) is explicitly deferred to a later API version and, if ever added, must be a DAG with cycle detection at validation time, never allowed to form a cycle. | Bounds the Reactive Engine's per-frame cost to O(layers × params × mappings), which is required for §87's 16.67ms budget. | **Y** — spec should say "v1 modulation is flat, non-recursive" explicitly. |
| 3.2 | §41 "Any animatable parameter eventually supports keyframes" and §27 puts "Keyframe Modifier" before "Audio Modifier" in the pipeline — but is the keyframe value a *base value replacement* at time T, or an *additional additive modifier*? These are very different behaviors (e.g. keyframing Opacity 0→1 while Beat also modulates Opacity — does audio modulate around the *interpolated keyframe value* or is it independent and summed?). | This is the single most user-visible behavior of "keyframes + audio reactivity coexist" (§41) — guessing wrong produces a materially different creative tool. | Keyframes always define the **base value** (interpolated per the curve at time T); all reactive/noise modifiers apply as deltas *on top of* that interpolated base, per the §27 pipeline order, then clamp. This matches how virtually every professional motion-graphics tool (AE, Nuke) composes procedural expressions over keyframed values, which is the explicit UX benchmark class (§4). | Confirms §27's pipeline ordering is authoritative and final; Parameter model needs `keyframeTrack: Optional<Curve>` as distinct from `reactiveMappings: List<ReactiveMapping>`. | **Y** — make this ordering explicit with a worked example. |
| 3.3 | §67/§145 "quarantine" — is quarantine per-plugin-instance-in-a-project, or per-plugin-globally-across-all-projects? A plugin that crashes on Project A's Layer 5 might work fine on Project B. | If quarantine is global, one bad interaction in one project silently removes functionality from every other project using that plugin correctly — this itself becomes a stability/trust bug. | Failure telemetry (crash count, category) is tracked **per plugin id+version globally** (it is the plugin code that is suspect, not the project), but quarantine state is exposed to the user with full context: "Plugin X failed N times across M projects, most recently in 'Project A' at Layer 'Logo'." Global disable, but full transparency and a manual "re-enable and retry" escape hatch — never a silent, unexplained loss of capability. | PluginRegistry needs a durable failure-count/instance-log table distinct from ProjectState. | **Y** |
| 3.4 | §68/§69 "Plugin API is versioned... plugins declare minimum/tested API" but does not say whether the **host API is additive-only (never-breaking, SemVer-minor-only)** or can introduce breaking major versions that orphan old plugins. §153/§154 imply indefinite forward extensibility, which argues for additive-only, but §68's explicit "API 2.0" example implies breaking versions are expected. | Determines whether "certified" plugins have any long-term durability guarantee at all — critical to user trust in the "install once, keep working" promise threaded through §72/§150. | Adopt **SemVer for the Plugin API**: MINOR/PATCH are strictly additive/non-breaking (existing plugins keep working forever against a newer MINOR host); MAJOR is allowed but must ship with (a) an automatic compatibility shim layer for at least N-1 major versions where mechanically possible, and (b) mandatory migration-note tooling. Plugins declare `apiVersion` (major.minor) they were built against; host refuses to load a plugin whose declared major differs from any major the host doesn't have a shim for. | Plugin Runtime needs a version-shim registry, and PLUGIN_API.md must define the deprecation policy explicitly (e.g. "major versions supported for shim for 2 years / N host releases"). | **Y** |
| 3.5 | §92/§137 "background execution" for export — ambiguous whether export can *literally* run for the 3–8 minutes a 4K60 multi-minute video export takes while the user backgrounds the app, given Android's foreground-service and Doze constraints, or whether the spec intends "user can switch apps briefly, but export is app-lifetime-bound." | Determines whether a Foreground Service with a persistent notification (required for genuinely long-running background work per Android policy) is mandatory infrastructure, which is a real manifest/permission/UX commitment (notification, `FOREGROUND_SERVICE` type declarations), or optional. | Export runs in a **Foreground Service** (`dataSync`/`specialUse` type as appropriate) with a persistent progress notification from the moment export starts; this is the only way to satisfy §92 (progress/ETA/cancel), §95 (survive backgrounding/screen-off/config changes), and §137 together on real Android without being killed. | Adds a manifest permission + notification-channel requirement and a Service lifecycle to the Export Engine design — not optional infra. | **Y** — make Foreground Service explicit, not implied. |

## 4. Missing Interfaces / Contracts Between Subsystems

| # | Missing contract | Why it matters | Recommendation | Consequence | Spec change |
|---|---|---|---|---|---|
| 4.1 | No formal **Renderer ↔ Reactive Engine** contract — §22–§29 describe modulation conceptually, §88–§89 describe GPU resource ownership, but no interface defines how a resolved (post-clamp) parameter value for frame T actually reaches a shader uniform or a CPU-side transform matrix. | Without this contract, individual layer implementations will each invent their own way to "ask" for a modulated value, producing per-layer inconsistency and defeating §26 (any parameter, any target). | Define `ParameterResolver` interface: `resolve(parameterId: ParamRef, timestampT: Time): ResolvedValue`. Every renderable (layer, effect, shader uniform) holds `ParamRef`s, never raw values, and the Renderer calls the resolver once per frame per referenced parameter (memoized within the frame) before building draw calls. | This is the actual mechanism that satisfies §154 ("host provides Parameters, Reactive engine, Render context") — it must be specified as a named interface, not left as "the engine handles it." | **Y** |
| 4.2 | No formal **Project State ↔ Renderer State** contract for how edits become visible — §102 draws the unidirectional diagram but doesn't define whether the Renderer holds its own derived/cached scene graph (for performance) or re-derives it from ProjectState every frame. | Determines whether "Renderer State" is a real, separate, cacheable structure (needed for 60fps performance — you cannot afford to rebuild GPU resource bindings from JSON-like ProjectState every frame) or just an alias for ProjectState (simpler but implies naive performance). | Renderer maintains a **derived RenderGraph** (a compiled, GPU-resource-bound representation) that is incrementally updated via a diff/patch stream from ProjectState (command-based, matching §85's Undo/Redo commands 1:1) — never rebuilt wholesale except on load. Each Undo/Redo command has a corresponding RenderGraph patch operation. | This makes Command objects (§85) do double duty: they are both the undo/redo log AND the ProjectState→RenderGraph diff protocol. Must be designed together, not sequentially. | **Y** |
| 4.3 | No contract for **how a plugin's declared "reactive target" actually becomes settable** by the host's Reactive Engine (§50–§52) — i.e., what does the plugin *implement* vs. what does the host *inject*? | This is the crux of the entire "plugins get audio-reactivity for free" promise (§50). Without a concrete interface it is just aspiration. | Plugin parameters marked `supportsReactive: true` are, from the plugin's perspective, **write-only sinks**: the plugin defines a `setParameter(id, value)` entry point (or, for shader params, simply declares which uniform name maps to which parameter id — the host writes the uniform directly, the plugin's shader never even calls a "get audio" function). The plugin never queries audio state itself; the host resolves the modulated value (per 4.1) and pushes it in before invocation. This is what makes §60's "plugins don't get arbitrary engine access" and §50's "automatic reactivity" simultaneously true. | Plugin Effect/Visualizer entry point contract: `render(inputs: RenderInputs, resolvedParams: Map<ParamId, Value>) -> Texture`. No access to raw audio, no access to other layers, no access to project state. | **Y** — this resolves what would otherwise be read as a contradiction between §50 and §61/§62. |
| 4.4 | No contract for **Asset Registry ↔ Storage Access Framework** persistence — §82 requires stable asset IDs decoupled from filesystem paths, but SAF URIs can lose permission (revoked grant) or become invalid (file moved/deleted by another app) between sessions. Nothing specifies the recovery contract. | Silent SAF permission loss is one of the most common real-world Android media-app bugs ("my images disappeared"). Without a defined contract, this becomes an unhandled `SecurityException` crash. | AssetRegistry entry includes `uri`, `persistedPermissionTaken: Boolean`, and a `lastKnownHash`. On project load, the registry validates each asset lazily (on first use, not eagerly for all assets) and on failure surfaces a **Relink Asset** flow (matches §72's "Missing Plugin" placeholder pattern, applied to assets: "Missing Asset — Relink"), never a crash. | Asset loading must always be wrapped in a recoverable-error path feeding the Layer Panel's placeholder rendering, not a direct decode call in the render loop. | **Y** — add explicit "Missing Asset" behavior alongside §72's "Missing Plugin." |
| 4.5 | No contract between **Timeline Engine and Reactive Engine** for how `timelineRange` (§11, per-layer active range) interacts with modulation continuity — if a layer becomes active at T=5s, does its envelope-follower/peak-gravity state start "cold" (as if audio was silent before) or does it reflect the true audio history from T=0? | Affects correctness of the very first frames a layer is visible for (e.g. a peak-hold value that should already be "warm" from bass hits before the layer entered). Left unspecified, results will be inconsistent and hard to golden-test. | Per §1.3's resolution: all temporal modulator state is **re-derived deterministically from the analysis cache from a fixed epoch**, independent of layer visibility. A layer's modulator sees the true audio history regardless of when the layer itself becomes visible — visibility is a purely visual/compositing gate applied after modulation resolution, not a reset of modulator state. | Layer visibility (`timelineRange`) must be implemented as a final compositing mask, never as a lifecycle event that resets or short-circuits Reactive Engine computation. | **Y** |

## 5. Dependency & Coupling Risks

| # | Risk | Why it matters | Recommendation | Consequence | Spec change |
|---|---|---|---|---|---|
| 5.1 | §116's module list places `reactive/` and `renderer/` as siblings with no stated dependency direction; §117 states high-level ownership rules but not an enforceable module dependency graph. Without an enforced graph, `renderer/` code will end up importing `reactive/` internals directly (fastest path for an engineer under deadline pressure) rather than through the ParameterResolver contract (4.1). | This is exactly the erosion path that turns a modular platform into the monolith §157 forbids — it happens gradually, one "just this once" import at a time. | Adopt a **strict layered module dependency graph** (see §20.B below) enforced by build-system visibility rules (Gradle module `api`/`implementation` boundaries, or a lint/Danger check that fails CI on disallowed imports). Direction: `core/model` ← `audio` ← `reactive` ← `renderer` ← `layers`/`effects` ← `plugins` ← `ui`. No back-edges permitted; `plugins` never imports `renderer.opengl` internals, only `plugins.api`. | Requires setting up module boundaries and a dependency-direction CI check **before** Phase 1 code lands, not retrofitted later. | **Y** — add the enforced graph to §116/§117. |
| 5.2 | Plugins are asked to register new **Layer types** (§57) and new **Reactive Sources** (§55) that must appear in host UI menus (§17 "Add Layer", reactive source pickers) — this requires the UI to enumerate plugin-contributed metadata, which is a two-way dependency (`ui` must query `plugins.registry`, and `plugins.registry` must not know about `ui`) that's easy to implement backwards (plugin code directly pushing Compose UI elements into the host, which would violate §48's "declarative, not Compose-modifying" rule). | Getting this direction wrong reintroduces the exact "plugin author has to touch host source" problem §150/§43 are designed to eliminate. | PluginRegistry exposes a passive, queryable `List<LayerTypeDescriptor>` / `List<ReactiveSourceDescriptor>`; `ui` polls/observes the registry (e.g. via a Flow/StateFlow) and renders menus from descriptors. Registry has zero dependency on `ui` or Compose. | Confirms the UI Schema (§47/§48) must be able to fully describe a menu *entry* (icon, label, category) as well as a *settings panel* — not just parameter controls. | N (implementation detail, but must be designed explicitly) |
| 5.3 | §36 "Effects are modular... can be chained" plus §37's list implies effects operate on arbitrary intermediate textures, but nothing bounds how many chained effects/layers can exist before FBO/texture memory exhausts a device (§12's `GroupLayer` nesting compounds this: nested groups × per-layer effect chains × masks can create an unbounded FBO ping-pong depth). | Uncapped resource fan-out is the single most common cause of `OUT_OF_MEMORY`/`GPU_ERROR` (§97) on real Android GPUs, and directly threatens §87's 60fps target on anything but a flagship device. | Renderer enforces a **hard, configurable resource budget** (max concurrent FBOs, max texture memory, max effect-chain depth, max GroupLayer nesting depth — e.g. depth ≤ 8) validated at *project-edit time* (warn/block adding another effect once budget is hit) not just discovered at render time. Preview Quality mode (§86) scales this budget down further on lower-end hardware per §96's hardware capability detection. | TextureManager/FramebufferManager need a budget-tracking allocator with a query API the UI can call *before* letting the user add another effect/layer, not just a runtime failure mode. | **Y** — add explicit resource-budget requirement to §88/§96. |

## 6. Rendering Architecture Risks (GPU/CPU Synchronization)

| # | Risk | Why it matters | Recommendation | Consequence | Spec change |
|---|---|---|---|---|---|
| 6.1 | Audio analysis (CPU, possibly on a background thread pool) and rendering (GPU, on the render thread via GLSurfaceView/GL thread) must agree on "the value of Bass at timestamp T" every frame — but §101 only says "separate threads," not how cross-thread reads happen safely without either blocking the render thread (missing 16.67ms budget, §87) or reading torn/stale data. | A naive shared-mutable-map-of-latest-values approach will produce frame tearing (some layers see t=100ms's Bass, others see t=116ms's) and possible torn reads (non-atomic multi-field structs) — subtle bugs that only show up under load. | The AudioAnalysisCache is **immutable-once-written, append-only, and randomly-readable** (like a sorted array indexed by time). The render thread never blocks on audio analysis catching up to real-time preview playback; if analysis for time T is not yet cached (e.g. very start of playback before background analysis completes), the renderer uses the nearest available cached sample and flags the frame as "analysis pending" in diagnostics, never blocks. For **export**, analysis must be 100% precomputed before any frame is rendered (export is not real-time, so this is always achievable and must be enforced as a precondition). | AudioAnalysisCache API must be lock-free-readable (e.g. a versioned, append-only ring/array behind an atomic "highest complete index" marker) — a real concurrency design task, not "just use a HashMap." | **Y** — add explicit concurrency contract for AudioAnalysisCache. |
| 6.2 | §88 "never create expensive GPU resources every frame" is correct but unenforceable as stated — nothing defines *which* resources are "expensive" nor a lifecycle (create-on-demand, pooled-reuse, explicit-release) for FBOs/textures tied to dynamically added/removed layers and effects during live editing. | Without an explicit resource lifecycle, the natural implementation pattern (allocate FBO when layer is added, in the Compose-triggered recomposition path) risks allocating/freeing GPU resources on the *UI* thread or at unpredictable times relative to the GL thread's EGL context, which is a well-known source of GL error / crash on Android (`GL context not current on this thread`). | All GPU resource allocation/deallocation happens **exclusively on the GL thread**, driven by a command queue that UI/edit actions post into (never a direct call from Compose/ViewModel into GL objects). |---|---|---|---|---|---|
| 15.1 | §120's golden-render tolerance is unspecified ("compare against golden reference with defined tolerance" — but the tolerance itself isn't defined, nor is the comparison metric: exact pixel match, PSNR/SSIM threshold, or perceptual diff). GPU rendering is **not bit-exact across GPU vendors/drivers** even for identical shader code (differing float precision, blend hardware behavior) — an exact-match golden test would be permanently flaky across the device matrix (§122). | An improperly specified golden-test tolerance is worse than no golden tests: it either produces constant false-positive failures (eroding trust, leading engineers to ignore/disable them — the exact "hack stack" failure mode §123 warns against) or, if tolerance is too loose, silently misses real regressions. | Golden render comparison uses a **perceptual metric (SSIM or similar) with a documented per-test-category threshold**, computed on a fixed reference GPU/driver combination (e.g. a specific emulator/CI device image) so tolerance only needs to absorb the test's own intentional randomness sources (none, since determinism is required) plus negligible floating-point noise — not cross-device variance. Golden tests run in CI on a pinned environment; device-matrix testing (§122) is a separate, looser "does it crash / is it roughly right" tier, not the same golden-pixel-diff tier. | Testing architecture must explicitly split into **CI Golden Tests** (pinned environment, strict SSIM threshold, deterministic) vs. **Device Matrix Smoke Tests** (real/varied hardware, crash/perf/rough-correctness only) — conflating them as the spec currently does is unworkable. | **Y** |
| 15.2 | §78/§79/§80 (layer/effect/plugin isolation tests) are excellent as *stated intent* but are not specified as **automated, CI-enforced regression tests with a fixed fixture project** — as written they could be satisfied by one-time manual verification, which provides no protection against future regression (directly contradicting §123's "no hack stack" and §125's "Claude must self-diagnose" via automated means). | Isolation is the single most architecturally load-bearing property this whole spec depends on (§2's "core differentiator"); it must be the most rigorously *continuously* tested property, not a one-time check. | These three isolation tests become **permanent, named CI test cases** (`test_layer_isolation_golden`, `test_effect_isolation_golden`, `test_plugin_isolation_golden`) using the exact fixture from §141/§142, run on every commit, using the golden-render infrastructure from 15.1 — never removed, never skipped, treated as release-blocking per §148. | Elevates §78–§80 from "principles" to "named, permanent, CI-blocking test IDs" referenced directly in the Production Readiness Gate (§148). | **Y** |
| 15.3 | No test category addresses **plugin API version-skew** (an old plugin against a new host, per §68/3.4's SemVer policy) as an automated, repeatable test — without this, the "additive-only host API" promise (3.4) is unverifiable and will silently rot as the host evolves. | Given §150–§153's entire vision depends on plugins continuing to work indefinitely, this is not an optional test category — it's the primary evidence the extensibility promise is being kept release over release. | Maintain an **archive of every certified plugin version ever released** (even internal/example ones) as a permanent regression corpus; CI runs the full validation+golden-render pipeline (§63/§76) against every archived plugin version on every host release, flagging any that newly fail (host API regression) before release. | Adds a "Plugin API Compatibility Regression Suite" as a named, permanent CI stage, growing over time — a real but necessary ongoing cost, and the only way §68's promise is actually enforced rather than aspirational. | **Y** |

## 16. Security Risks — Dynamically Installed Extensions

| # | Risk | Why it matters | Recommendation | Consequence | Spec change |
|---|---|---|---|---|---|
| 16.1 | §46 lists `signature` in the plugin manifest but nothing specifies **whose signature, verified how, against what trust root** — without a defined trust model, "signature" is decorative, and a malicious `.arp` file could be installed by simply having *some* self-signature (or none, if verification isn't actually implemented). | For a system explicitly designed around sideloaded third-party executable-adjacent content (WASM per 9.1) running with GPU/audio access, an undefined trust model is a critical gap, not a nice-to-have. | v1 trust model: `.arp` packages are **not required to be centrally signed by the app publisher** (there is no plugin store implied by the spec), but the manifest signature is a **self-signature the host uses for integrity + update-authenticity** (detect tampering between versions, confirm "update" claims actually come from the same author key as the original install) — not an authorization/trust signal. The actual security boundary is the **sandbox** (declarative-only for GPU code, WASM fuel/memory-limited for logic, no `NETWORK` per 9.4, no filesystem/IPC/reflection), not the signature. The install-time UI must be explicit with the user: "This extension has not been reviewed by [publisher]; it runs in a restricted sandbox with no file, network, or system access" — never implying app-store-style vetting that doesn't exist. | This resolves an otherwise-unstated assumption; PLUGIN_SECURITY.md must state plainly that signatures are integrity/authorship continuity only, and sandboxing is the actual security control. | **Y** |
| 16.2 | Shader code (GLSL, per §45/§89) is treated as "declarative" (§60) and implicitly safe, but GLSL is a real, Turing-incomplete-in-practice-but-resource-unbounded language: a malicious/buggy fragment shader can contain unbounded loops (driver-dependent behavior, from a hang to a GPU driver crash/TDR that can affect the whole device on some Android GPU drivers, not just the app). | Treating "just a shader" as inherently sandboxed is a common but incorrect assumption — GPU driver crashes from hostile shaders are a real, documented attack class (denial of service at minimum, and historically a source of driver-level vulnerabilities). | Shader validation (§63 "Shader Compilation") must include **static analysis for unbounded loops** (reject any loop without a compile-time-constant, host-enforced-maximum iteration bound — a standard mitigation, e.g. requiring all loops to be `for` loops over a manifest-declared constant ≤ a host maximum) and the Sandbox Render test stage must run with a **watchdog timeout** that force-terminates (via EGL context loss recovery, per 6.3/1.5) any single draw call exceeding a bounded GPU time, treating this as an automatic validation failure (plugin never certified), not merely a runtime quarantine trigger after the fact. | Plugin Validator's "Shader Compilation" stage must be a real static-analysis pass, not merely "does `glCompileShader` succeed" — this is a meaningfully larger engineering task than the spec's phrasing implies. | **Y** |
| 16.3 | §62 "Plugin must NOT automatically receive... Android system APIs" is correct in principle but doesn't address the **WASM host-function surface** (9.1/1.2) concretely — i.e., exactly which host functions are exposed into the WASM linear-memory sandbox (the ABI from 1.2) is itself the entire attack surface, and an overly generous or carelessly implemented host-function set (e.g. one that happens to expose a raw pointer/length pair without bounds checking) reintroduces memory-safety risk despite WASM's own sandboxing. | WASM sandboxes are only as safe as their host-function (import) surface — this is the actual place where security bugs in this architecture will occur in practice, and the spec doesn't mention it exists as a design surface at all. | Define the WASM ABI as an explicit, minimal, versioned, **capability-typed** function table (e.g. `read_audio_feature(featureId: u32) -> f32`, `emit_particle(x: f32, y: f32, ...)` — never a generic `read_memory(ptr, len)` or callback-into-host-object pattern). Every host function is individually reviewed as part of PLUGIN_SECURITY.md and is the *only* thing a WASM Analyzer/Layer/Generator plugin can ever do — this list is the actual security boundary and must be treated with the rigor of a syscall table, not an implementation afterthought. | Adds "WASM Host ABI Specification" as a mandatory, security-reviewed artifact (part of PLUGIN_API.md/PLUGIN_SECURITY.md) before any WASM plugin type ships. | **Y** |

## 17. Technically Unrealistic or Overcomplex Requirements

| # | Requirement | Why it's risky as stated | Recommended simplification | Consequence | Spec change |
|---|---|---|---|---|---|
| 17.1 | §6 "architecture must permit a future VulkanBackend" with business logic never depending on a specific graphics backend, on top of an already-large v1 scope (full plugin platform + WASM sandbox + GPU compositor + Media3 export). Designing a *true* backend-agnostic abstraction (not just an interface with one implementation) that genuinely supports both a fixed-function-ish OpenGL ES model and Vulkan's fundamentally different resource/command-buffer model, without ever having built the second backend to validate the abstraction, is a well-known trap (a "future-proof" abstraction built against one real implementation is usually wrong and gets rewritten anyway when the second backend actually arrives). | Time spent generalizing `RendererBackend` against a backend that doesn't exist yet is time not spent on the actually-hard, actually-required v1 problems (audio-reactive compositing, plugin sandboxing) — and it is likely to produce the *wrong* abstraction anyway. | Keep `RendererBackend` as a **real interface boundary** (renderer.core never calls `GLES20.*` directly, always through the abstraction) so that a second backend is *possible without a rewrite of business logic* — but do not attempt to pre-design Vulkan-specific concepts (explicit command buffers, memory barriers, descriptor sets) into the v1 abstraction. Treat this as "leave the door open," not "build the second room." | Scopes §6 down from an active engineering commitment to an architectural discipline (module boundary enforcement, per 5.1) — same intent, far less v1 cost. | **Y** — reword §6 to distinguish "boundary discipline now" from "Vulkan support now." |
| 17.2 | §157 "do not use global mutable state" as an absolute, combined with real Android GPU/audio realities (an `EGLContext`, an `AudioTrack`, a `MediaCodec` surface — these *are*, unavoidably, process-global-ish singleton resources by platform design) makes the rule as literally stated unsatisfiable, and "absolute rules that are actually violated everywhere in practice" train engineers to ignore architectural rules generally. | An unenforceable absolute rule is worse than a precise, enforceable one — it either gets silently violated everywhere (undermining the review process) or blocks legitimate, necessary platform-singleton usage. | Restate precisely: **no *ad hoc, implicit, untyped* global mutable state** (e.g. static mutable maps used as a poor-man's event bus or cache) — but a small, explicit, documented set of **owned platform singletons** (one `GLContextHolder`, one `AudioEngine` instance, injected via DI rather than referenced as bare statics) is fine and necessary. The distinction is explicitness/ownership/testability, not "zero singletons." | Makes §157 actionable in code review rather than aspirational; should be paired with a DI framework choice (e.g. Hilt) as part of Phase 0's technology decisions. | **Y** |
| 17.3 | §63's validation pipeline for *every* plugin install includes "Performance Test" and "Regression Test" — for a simple, purely-declarative Effect plugin (a shader + a handful of float parameters, §51's Chromatic Aberration example), running a full performance benchmark and a regression suite on-device at install time (not in CI, on the *user's* phone, per §64's Plugin Laboratory framing) may be disproportionate latency for what should feel like an instant "install and use" action for the common case. | If every plugin install — even the simplest, most common case — takes tens of seconds of on-device benchmarking before the effect is usable, this directly undermines §43's promise that installing extensions should feel lightweight and immediate, hurting adoption of the entire extension-platform value proposition. | Split validation into **fast-path** (manifest schema, shader static analysis/compile, parameter schema validation — sub-second, always run synchronously at install) and **slow-path** (on-device performance benchmark, extended regression/golden-render) that runs **asynchronously after install**, with the plugin usable immediately in a "Validated" (not yet "Certified") state, upgrading to "Certified" silently once slow-path completes, and only *downgrading* (with user notice) if slow-path later finds a real problem. | Refines the plugin state machine (§66) to include an explicit "Validated (fast-path only)" state distinct from "Certified," changing install-time UX from blocking to progressive. | **Y** |

### D. Render Architecture & Render Graph

- **Single RenderGraph**, derived from ProjectState via the Command-diff protocol (4.2), consumed identically by preview and export (A).
- Node = compositing operation: `LayerNode → [EffectNode]* → BlendNode → parent GroupNode/FinalNode`.
- Each Node references `ParamRef`s only; the per-frame resolve pass (ParameterResolver, 4.1) computes all referenced values once (deduplicated per source, §7.3) before any draw call is issued.
- GPU resource lifecycle is queue-driven on the GL thread only (6.2); resource budget enforced at edit time (5.3).
- Coordinate space: logical units normalized to canvas height (2.1); color compositing in linear light (2.2).
- EGL/GL context loss and configuration changes are routine, recoverable events (6.3, 14.3): full resource rebuild from ProjectState, never a fatal path.

### E. Audio Analysis Architecture

- `AudioDecoder → AudioAnalyzer (chunked, priority-ordered per 7.1: waveform → RMS/peak → FFT bands → onset/beat → chroma) → AudioAnalysisCache`.
- Cache: content-addressed by `(assetHash, analysisConfigHash)` (10.1), external to the project file, regenerable, stored at fixed 100Hz feature rate (2.6) in an efficient binary format (memory-mapped, versioned).
- Lock-free, append-only, randomly-readable by timestamp (6.1); analysis-in-progress frames degrade to nearest-available sample, never block the render thread.
- Analyzer Plugins (WASM, 1.2/9.1) contribute additional named features into the same cache format, indistinguishable to consumers from built-in features (§55/§56).

### F. Reactive / Modulation Architecture

- Pipeline (confirmed order, 3.2): `KeyframeTrack(t) → Σ/×/max/min(ReactiveMapping outputs, ordered, per 2.4) → Clamp → ResolvedValue`.
- Every temporal modulator (envelope follower, peak/gravity) is a **pure function of the analysis cache from a fixed epoch** (1.3/4.5) — never ambient mutable state.
- **Resolved Modulation Cache** (8.2): precomputed per (parameter, mapping-config-hash) at the same 100Hz rate, invalidated only by mapping-config edits — makes scrubbing O(1) and guarantees preview/export/dropped-frame identity (11.2).
- Source evaluation deduplicated per unique source definition per frame (7.3).
- v1 modulation graph is flat/non-recursive (3.1); meta-modulation explicitly deferred.

### G. Timeline Architecture

- Playhead position drives requested render timestamp T (audio-clock-master in preview, frame-clock-master in export — 2.3).
- `timelineRange` per layer is a pure **compositing visibility gate**, applied after modulation resolution (4.5) — never a modulator-state reset.
- Undo/redo commands double as the ProjectState→RenderGraph diff protocol (4.2); continuous-edit coalescing via a same-target debounce rule (8.3).

### H. Plugin / Extension Platform Architecture

- Two execution tiers (1.2): **Declarative** (manifest + GLSL, Effect/Visualizer plugins, no arbitrary logic) and **Sandboxed WASM** (Analyzer/Layer/Generator-with-logic plugins, minimal capability-typed host ABI — 16.3).
- `NETWORK` permission removed from v1 permission set entirely (9.4).
- Validation pipeline splits into **fast-path** (sync, sub-second: manifest/schema/shader-static-analysis-compile/parameter validation) and **slow-path** (async, post-install: performance/regression/golden-render) — 17.3; plugin states extend to `Validated (fast-path) → Certified (slow-path passed)`.
- Shader static analysis rejects unbounded loops; sandbox render runs under a GPU watchdog timeout (16.2).
- Quarantine is two-phase: immediate soft-disable (placeholder render) + deferred hard GL-context rebuild at next safe restart (1.5).
- Failure tracking is per plugin id+version, globally, with full user-facing transparency (3.3).
- Dependency activation is transactional/all-or-nothing (9.2).
- Every plugin-contributed serializable type declares a `migrate()` hook (9.3); Plugin API is SemVer, additive-only for minor/patch, shimmed for N-1 majors (3.4).
- Built-in visualizers/effects ship as first-party "system plugins" on the exact same public API (18.1) — the strongest validation of platform completeness.

### I. Project File Format & Versioning Strategy

- Versioned JSON (§81/§84), `schemaVersion` field, forward migration chain v1→v2→...→vN, each step covered by a mandatory migration golden-render test (10.2).
- Analysis cache and derived preview data (waveform peaks, video proxies) are **excluded** from the portable project file — external, content-addressed, regenerable (10.1, 14.1, 19.2).
- Asset references are stable IDs + SAF URI + hash; missing/permission-lost assets degrade to a "Missing Asset — Relink" placeholder, never a crash (4.4).
- Plugin references store `pluginId`+`pluginVersion`; a project opened without an installed plugin shows a "Missing Plugin" placeholder and remains otherwise editable (§72).

### J. Preview / Export Architecture

- One RenderGraph, two consumers (A, D). Draft-mode reductions are strictly **quality knobs** (resolution/AA/blur-kernel size) — never **content knobs** (particle count, procedural seeds), which are project settings identical across preview and export (11.1).
- Export renders every frame with fully precomputed analysis (6.1) directly into the encoder's input `Surface` via a shared EGL context — no CPU readback in the steady-state path (13.3).
- Export runs in a Foreground Service (3.5/14) with pre-flight `MediaCodec` capability probing (13.1) and a bounded, error-taxonomy-driven single-retry policy (13.2).

### K. Testing & Self-Diagnostic Architecture

- **CI Golden Tests**: pinned environment, SSIM-threshold comparison, fully deterministic (15.1) — includes the permanent, named isolation suite (§78–§80 → 15.2) and the migration golden suite (10.2).
- **Device Matrix Smoke Tests**: real/varied hardware, crash/perf/rough-correctness only, separate tier (15.1, §122).
- **Plugin API Compatibility Regression Suite**: every archived certified plugin version re-validated against every new host release (15.3).
- Debug Overlay breaks CPU time down per subsystem (12.3); Diagnostics exports a full report (§98).

### L. Performance Strategy

- Explicit, ordered **Quality Degradation Ladder** (12.1): resolution scale → AA/post quality tier → (manual-only) content-level settings → frame-rate fallback. Content values never silently reduced.
- Per-subsystem CPU budgets within the 16.67ms frame (12.3).
- Asset decode-for-purpose (preview-resolution vs. export-resolution) with headroom factor (12.2); GPU resource budget enforced at edit time (5.3); proxy generation for heavy video (19.2).

### M. Security Model

- Sandbox, not signature, is the security boundary (16.1); signature is integrity/authorship-continuity only, communicated honestly to the user at install time.
- No `NETWORK` capability for any v1 plugin type (9.4).
- WASM host ABI is a minimal, versioned, capability-typed function table, security-reviewed as a first-class artifact (16.3).
- Shader static analysis + GPU watchdog prevent hostile/buggy shaders from affecting device stability beyond the sandboxed plugin (16.2).

### N. Failure / Recovery Strategy

- GL/EGL context loss and configuration changes are routine, recoverable (6.3, 14.3) — full GPU resource rebuild from durable ProjectState.
- Plugin quarantine: two-phase soft/hard (1.5); global failure tracking with transparency (3.3); transactional dependency activation (9.2).
- Export failure: bounded single retry with capability-matched fallback, full diagnostics otherwise, never overwrite prior success (13.2, §94).
- Missing asset / missing plugin: placeholder + relink/keep-editable, never crash or silent data loss (4.4, §72).
- Memory pressure (`onTrimMemory`) releases cheap-to-regenerate caches first, protects ProjectState/undo history always (14.2).

### O. Development Phases & Dependency Order (refines §128–§148)

0. **Architecture Gate** (this document) — ratify all flagged spec changes before any code.
1. **Foundations**: `core/model`, module dependency-boundary CI check (5.1), DI setup, Coordinate/Color/Clock decisions (2.1–2.3) implemented as testable primitives before any UI.
2. **Audio Engine**: decoder/playback/analysis/cache, progressive analysis (7.1), waveform trim UI (16 — using the derived-cache tier, 14.1).
3. **Minimal Compositor**: Image/Video/Text/Shape/Solid/Group layers only (18.1's "true core set"), transforms, blend modes, preview path, GL resource-queue architecture (6.2/6.3).
4. **Reactive Engine**: ParameterResolver (4.1), Resolved Modulation Cache (8.2), envelope/peak-gravity as pure functions (1.3), source dedup (7.3) — validated against the layer-isolation golden test (§78) as the phase-exit criterion.
5. **Built-in Visualizers/Effects as first system plugins** (18.1) — this is simultaneously Phase 4/5 of the original spec *and* the first real exercise of the Plugin API (H), forcing the API to be correct before any third-party plugin exists.
6. **Timeline & Keyframes**: coalescing (8.3), keyframe/reactive composition (3.2).
7. **Plugin Platform proper**: declarative tier fully generalized from #5; WASM tier (Analyzer/Layer/Generator) added with sandbox/validator/quarantine (H, M).
8. **Export Engine**: capability probing, Foreground Service, GPU-surface hand-off (J).
9. **Project Management**: autosave/recovery/migration golden suite (I, 10.2).
10. **Performance Hardening**: degradation ladder, budgets, proxies (L).
11. **Production QA**: full gate (§148) including Plugin API Compatibility Regression Suite (15.3) and device matrix (§122).

Each phase's exit criterion is a passing, permanent, named CI test — not a demo.

## 21. ARCHITECTURE GATE — REQUIRED DECISIONS BEFORE IMPLEMENTATION

No production code (core or plugin) may be written until each of the following is explicitly ratified (owner: project decision-maker; this document proposes a default for every item so ratification can be "accept default" or "override"):

1. **Media3 scope boundary** — confirm Media3/MediaCodec is decode+encode+mux infrastructure only, never a compositing path (1.1).
2. **Plugin execution tiers** — confirm the Declarative/WASM split and that WASM ships in v1 for Analyzer/Layer/Generator-logic plugins, not deferred (1.2, 9.1).
3. **Determinism definition** — ratify the precise "pure function of (ProjectState, T, AnalysisCache)" definition and that all temporal modulator state is re-derived, never ambient (1.3, 4.5).
4. **Quarantine model** — ratify the two-phase soft/hard quarantine and that GL context loss is a routine, recoverable, tested path (1.5, 6.3, 14.3).
5. **Coordinate & unit system** — logical-unit canvas space, per-parameter unit metadata (2.1).
6. **Color working space** — linear-light compositing internally, sRGB at edges (2.2).
7. **Clock authority** — audio-clock-master in preview, frame-clock-master in export, as two intentionally distinct but both-deterministic regimes (2.3).
8. **Modulation combine semantics** — ordered list + `combineOp` per parameter, flat/non-recursive in v1 (2.4, 3.1).
9. **Analysis cache resolution** — 100Hz (10ms hop) common feature timeline, interpolation rule (2.6).
10. **Keyframe/reactive composition order** — keyframe defines base value, reactive/noise modifiers apply as deltas on top, then clamp (3.2).
11. **Quarantine scope** — global per plugin id+version with full transparency, not per-project-silent (3.3).
12. **Plugin API versioning policy** — SemVer, additive-only minor/patch, shim window for majors, published deprecation policy (3.4).
13. **Export background execution** — Foreground Service with persistent notification, not best-effort backgrounding (3.5).
14. **ParameterResolver contract** — the single interface every renderable uses to obtain modulated values (4.1).
15. **RenderGraph as derived cache vs. ProjectState as sole source of truth** — command-based diff/patch protocol (4.2).
16. **Plugin reactive-target injection contract** — write-only `setParameter`/uniform-push model, plugins never query audio state directly (4.3).
17. **Missing-asset recovery flow** — relink placeholder, never crash (4.4).
18. **Module dependency graph & enforcement mechanism** — the layered graph in §20.B, enforced by build tooling from Phase 1 (5.1).
19. **GPU resource budget policy** — enforced at edit time, not just render time; exact budget numbers per device tier to be set during Phase 3 hardware survey (5.3).
20. **Cross-thread audio↔render concurrency contract** — lock-free, append-only, versioned cache; render thread never blocks (6.1).
21. **GL command-queue architecture** — all GPU resource mutation via a GL-thread-drained queue, never cross-thread direct calls (6.2).
22. **Progressive audio analysis ordering & UX** — waveform-first, deepening in background, non-blocking (7.1).
23. **Low-confidence reactive source behavior** — hold/decay to neutral, UI confidence indicator (7.2, 1.4).
24. **Source evaluation deduplication** — per unique source definition per frame, not per consumer (7.3).
25. **Per-type interpolation rules** — Angle shortest-arc, Color linear-space, etc., as part of Parameter type metadata (8.1).
26. **Resolved Modulation Cache** — precomputed per (parameter, mapping-config-hash) at 100Hz, invalidated only by mapping edits (8.2, 11.2).
27. **Undo coalescing rule** — same-target debounce window (default 400ms) (8.3).
28. **WASM validation stages** — ABI conformance, static resource limits, fuel-limited execution, determinism check (9.1).
29. **Transactional plugin dependency activation** — all-or-nothing (9.2).
30. **Plugin-contributed type migration hooks** — mandatory `migrate()` entry point (9.3).
31. **Remove `NETWORK` from v1 plugin permissions entirely** (9.4).
32. **Analysis cache exclusion from portable project files** — content-addressed, external, regenerable (10.1, 19.1 scope note).
33. **Migration golden-render test requirement** — mandatory per schema version bump (10.2).
34. **Quality-knob vs. content-knob classification** — mandatory per-parameter metadata on every effect/generator/particle system, enforced by review (11.1).
35. **Adaptive Quality Degradation Ladder** — explicit ordered list, content values manual-only (12.1).
36. **Decode-for-purpose asset policy** — preview-resolution vs. export-resolution texture variants (12.2).
37. **Per-subsystem CPU time budgeting & Debug Overlay breakdown** (12.3).
38. **Encoder capability pre-flight probing** at export-configuration time, not just app-launch (13.1).
39. **Bounded export retry policy** mapped to the §97 error taxonomy (13.2).
40. **GPU-surface (not CPU-readback) encoder hand-off** with shared EGL context (13.3).
41. **Three-tier asset caching** (original SAF asset / derived preview cache / analysis cache) (14.1).
42. **`onTrimMemory` response policy** across Renderer and Audio caches (14.2).
43. **Golden-test comparison metric & tolerance** — SSIM-based, pinned CI environment, separate from device-matrix smoke tests (15.1).
44. **Layer/Effect/Plugin isolation tests as permanent, named, release-blocking CI tests** (15.2, §78–§80).
45. **Plugin API Compatibility Regression Suite** — archive every certified plugin version forever, re-validate every host release (15.3).
46. **Plugin trust model** — signature = integrity/authorship continuity only; sandbox = actual security boundary; explicit non-vetting disclosure to users at install (16.1).
47. **Shader static analysis for unbounded loops + GPU watchdog timeout** as a validation-blocking (not just runtime) check (16.2).
48. **WASM host ABI** — minimal, versioned, capability-typed function table, security-reviewed as its own artifact before any WASM plugin ships (16.3).
49. **RendererBackend scope discipline** — real interface boundary now, no Vulkan-specific concepts pre-built (17.1).
50. **"No global mutable state" restated** as "no ad hoc/untyped globals; explicit owned/injected platform singletons are fine" (17.2).
51. **Fast-path/slow-path plugin validation split** — usable immediately post-fast-path, Certified after async slow-path (17.3).
52. **Core-vs-plugin boundary for built-ins** — all v1 visualizers/effects/templates ship as first-party system plugins on the public API, not hard-coded (18.1–18.3).
53. **Single-audio-track v1 scope** — explicitly stated, multi-track/ducking deferred (19.1).
54. **Video proxy workflow requirement** for heavy source video layers (19.2).
55. **Color grading scoped as a post-v1 Effect plugin operating on final composite** — confirms the plugin model supports a "final-output-scope" effect class (19.3).
56. **Accessibility requirements** added to UI NFRs (19.4).
57. **Opt-in crash/telemetry hook** reserved in Diagnostics architecture, off by default, per privacy stance (19.5).
58. **Technology confirmations**: Kotlin/Compose (given), DI framework choice (e.g. Hilt), WASM runtime choice (e.g. Wasmtime/Wasmer via JNI — needs a feasibility spike on Android before Phase 7 commitment), minimum supported Android API level (drives available MediaCodec/Compose/foreground-service capabilities — not yet stated anywhere in the spec).

**No implementation work should begin on any subsystem whose governing decision above is unresolved.** Where this document proposes a default, silence should not be read as approval — each item needs an explicit yes/override before its dependent phase (per §20.O) starts.
